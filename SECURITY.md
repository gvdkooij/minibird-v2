# Security review for Issue #1

Reviewed authentication and authorization: Argon2id password verification; server-side SQLite sessions with an opaque HttpOnly, SameSite=Lax session cookie; Secure by default; eight-hour expiry. All customer, settings, document and PDF routes require authentication. First-run initialization is transactional and must happen over a trusted local connection before public deployment. Five failed logins per peer within fifteen minutes are persisted in SQLite. Behind the reverse proxy the limit is shared; spoofed forwarded headers are ignored by the documented production command.

Reviewed CSRF: every mutation requires both a session-issued random token and a matching submitted token, including setup/login/logout. Tests include absent, forged and Unicode tokens. Tokens are rotated at authentication boundaries. Logout clears the browser cookie and revokes the corresponding server session. A delayed request cannot recreate the revoked session. There is no separate remote session revocation UI.

Reviewed injection and escaping: bound SQLite parameters; Jinja autoescaping; no user HTML marked safe; CSP blocks inline JavaScript; fixed numeric document routes and generated PDF names. Money uses finite bounded Decimal values with integer cents and explicit half-up rounding. Email addresses exclude header injection. SMTP always verifies TLS certificates through STARTTLS; secrets are encrypted at rest and never returned to forms or logs. SMTP host settings are available only to the trusted administrator; this app does not attempt to sandbox administrator-configured destinations.

Reviewed document integrity: transaction-protected unique counters, immutable customer/company snapshots, explicit status transitions, idempotent quote conversion and no deletion of issued documents. Deleted draft numbers are not reused. Issued corrections require an external linked credit note as documented. No bank integration or automatic payment reconciliation is implied.

Reviewed persistence and operations: versioned SQLite initialization, integrity-checked online backup, restore/restart test, default 0600 database permissions. Use a private data directory and unprivileged service with umask 0077. Preserve the encryption/session key outside source control. No public preview or external email was used during validation. User-supplied exports were tested only in temporary databases, without production deployment. HTTPS proxy and local initial setup are mandatory before public use; deployment remains an operator action.

Validation: 60 unit/integration cases and a Chromium workflow, clean installation, pip dependency checks and dependency vulnerability scan. The final dependency scan returned no known vulnerabilities at execution time; this is not a guarantee against undiscovered vulnerabilities. Tests use only temporary fictional data and mocked SMTP. This is an implementation review, not an independent penetration test.

## Import review

Authenticated, CSRF-protected two-phase uploads are limited to 50 MiB before multipart parsing and never become repository files or session-cookie contents. Pending previews are scoped to their initiating session; confirmed archives are admin-only downloads with fixed generated filenames. ZIP entries are inspected without extracting them: traversal, absolute paths, duplicate entries, encrypted entries, symlinks, excessive expansion and excessive entry counts are rejected. Nested XLSX archives are separately bounded; openpyxl uses defusedxml and loads cached values without external workbook links. UBL is parsed with defusedxml and DTDs forbidden. Untrusted filenames, names and descriptions are escaped by Jinja. No source-document text is treated as executable instructions.

Import runs in one SQLite transaction, rechecks the reviewed duplicate/link plan and never overwrites issued document records or existing customer fields. Imported documents are immutable, and the original PDF bytes are returned as downloads. Moneybird totals and tax subtotals are cross-checked before import. Repeated uploads, changed originals, ambiguity, rollback, schema-1 upgrades, persisted restart and authenticated archive retrieval have automated regression coverage. Uploaded personal examples were verified only in temporary test databases and are not committed as fixtures. Original archives and import metadata are financial/personal data; database backups need the same protection as the live database.

## Large upload and authentication regression fixes

The default browser upload path splits archives into 512 KiB requests, each checked for authenticated session ownership and an unpredictable CSRF header. Metadata, chunk and total sizes are independently bounded; part order and SHA-256 hashes prevent out-of-order or changed duplicate parts. Completed parts are deleted transactionally when the preview is created; retries of the completion return the same preview. Cancellation and expiry remove staged chunks. This does not increase the 10 MiB per-member and 64 MiB expanded-archive limits.

SameSite=Lax allows a top-level GET after an external Codespaces authentication redirect to retain the session. Every mutating endpoint still enforces CSRF. An authenticated, no-store GET returns the current CSRF token to same-origin JavaScript; CORS is not enabled. Uploads refresh stale tokens once, and confirmation/cancellation fetch a current token before submitting. Unauthenticated and forged requests remain rejected. Real Chromium regression coverage includes cross-site return, stale upload/confirmation forms and a supplied 17.3 MB export through an emulated 1 MiB per-request proxy limit, using only a temporary database. Tax-exempt UBL without a percent and undated draft quotes are covered without inventing dates or changing historical totals. Existing import fingerprints remain recognizable across this upgrade.

## Proxy-aware session error handling

Browser uploads no longer make an unconditional request to the separate token endpoint. They use the rendered form's CSRF token and refresh it only after a 403, by reading the authenticated same-origin import page. Confirmation reads the token from that same page. No CSRF check or authentication requirement has been removed. Successful same-origin redirects are accepted, while missing routes and proxy errors are reported with their HTTP status rather than being treated as session expiration. API callers requesting JSON receive a JSON 401/403 instead of an HTML redirect. Regression tests cover the legacy token endpoint being unavailable, a successful redirect during CSRF renewal, 503 and repeated 403 errors with preserved file selection, and an actual 401 login rejection. Only one CSRF retry is made.

## Session namespace and failure provenance

MiniBird uses its own `minibird_session` cookie instead of the generic `session` name. A separate generic cookie cannot overwrite its authenticated state; existing cookies belonging to other software are never deleted. The old cookie is not imported as authentication. Updating an existing instance requires a one-time login to issue the new cookie, preserving account/data. Tests reproduce an authenticated page followed by an immediate upload 401 when the old generic cookie is overwritten; the namespaced cookie prevents that reproduction in both TestClient and Chromium, including a full large-file import. This reproduction is evidence of collision resistance, not proof that a collision occurred in a user's inaccessible Codespace.

App responses carry a fixed `X-MiniBird-Response` marker. API authentication errors expose only non-secret reason codes for missing cookie, invalid cookie, and absent administrator authentication. The frontend distinguishes these from a 401 without the app marker; that unverified response is not presented as proof of an expired MiniBird session. No credential, cookie value or secret fingerprint is included. All authentication and CSRF requirements remain in force.

## Server-side session persistence

Schema 4 adds SQLite-backed authenticated sessions. Only successful authentication issues a random opaque cookie, and only authentication/logout rotates or clears it. Its secret-bound HMAC-SHA-256 hash is the database key; browser cookies do not contain administrator flags, upload ownership or preview IDs. These fields live server-side and concurrent changes are merged transactionally. Expired/revoked rows are never resurrected by late response writes. An independent signed pre-login cookie contains only the anonymous CSRF token, so an old anonymous response cannot overwrite the authenticated cookie. Old stateless cookies are not accepted as authentication; an upgrade requires one login, preserving all financial records and administrator credentials.

Chromium injects a cookie from an earlier anonymous page in the middle of a multi-part upload and completes the workflow. The supplied 17.3 MB archive was additionally tested with the same injection during chunk 16, through an emulated 1 MiB proxy limit; all 14 invoices and 6 quotes were imported in a temporary database. Parallel updates, late responses after logout, expiry, session persistence after app restart and schema-3 migration have regression coverage. Live Codespaces verification remains separate from these tests. Restore procedures explicitly revoke sessions recovered from backup.

The server-side session key is bound to MINIBIRD_SECRET through HMAC-SHA-256, so rotating the secret also invalidates existing login tokens. The raw opaque token is never stored in SQLite.
